Kubernetes と Cloud Run：管理する境界を選ぶ

制御ループ・Pod・Deployment・Serviceを理解し、マネージド実行基盤との違いを整理する。

更新: 2026-09-28

Kubernetes は宣言した状態へ実際のワークロードを近づけ続ける。Cloud Run はクラスタを利用者が管理せずにアプリを実行する基盤だ。単に同じ Kubernetes を誰が運用するかだけの違いではない。

制御ループ

Pod を落としたら「1回調整」を押す。差分検知 → 作成中 → 稼働、を止めて確認できる。自動調整は自分で開始する。

Deployment を作れば Service も自動作成されるわけではない。Service は別に宣言する。Pod は1個以上のコンテナを持ち、コンテナ再起動と Pod 自体の置換も別の出来事だ。

宣言の最低限の対応

apiVersion: apps/v1
kind: Deployment
metadata:
  name: example-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: example-api
  template:
    metadata:
      labels:
        app: example-api
    spec:
      containers:
        - name: api
          image: example.invalid/api:replace-before-use
          ports:
            - containerPort: 3000

これは構造説明用。実行前に実在するイメージへ置き換え、resources、probes、権限、設定などを追加する。selector と Pod の labels を一致させる。Service や外部公開はこの YAML には含めていない。

Cloud Run で残る責任

Cloud Run の HTTP service は HTTPS の入口、revision、スケーリングなどを提供する。終了まで動くバッチには jobs など、異なる実行形態がある。公式の実行形態で選択する。

利用者には次の責任が残る。

  • イメージと設定、IAM、公開範囲、秘密情報
  • concurrency・最大 / 最小インスタンスと DB 接続数
  • 永続化、アプリのタイムアウトと正常終了
  • エラー監視、料金、障害時の復旧

scale to zero はサービス全体の請求がゼロになる保証ではない。DB、ストレージ、ログ、ビルドなどは別に扱う。コールドスタート時間も固定値ではない。

選定の軸

Kubernetes は配置、ネットワーク、周辺機能を詳しく制御できる一方、管理する設定と障害領域が増える。マネージド Kubernetes でもアプリの運用が不要になるわけではない。

Cloud Run はクラスタ管理を省けるが、実行契約に合わせた設計が必要になる。「サービス数が何個なら必須」と決めず、必要な制御、運用体制、移植性、総費用で選ぶ。AWS 等との比較も、名称だけで完全に同等とは考えない。
