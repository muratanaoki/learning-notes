テスト設計：範囲と失敗の種類

unit・integration・HTTPテストを固定比率ではなく、守りたいリスクから配置する。

更新: 2026-09-06

テストピラミッドは、狭く速いテストと広い経路のテストを組み合わせる考え方だ。必ず同じ比率・実行時間になる法則ではない。

何を本物にするか

範囲主に守ること例
unitロジックと境界条件金額計算、状態遷移
integration接続先との契約実 DB の制約、SQL、マッピング
HTTP / E2E利用者から見た経路ルーティング、認証、DTO、応答

E2E と呼んでいても外部認証や決済を置き換えている場合がある。名称より、通す範囲と置き換えた境界を明記する。

テストダブルの役割

stub は決めた応答を返し、spy は呼び出しを記録し、mock は期待するやり取りを検証し、fake は簡略な実装を提供する。実際のツールでは複数の役割を兼ねる。

Map の fake repository は、DB の UNIQUE 制約、分離レベル、NULL、日付、SQL 方言を再現しない。モックした DB のテストが通っても、実 DB とつながる証拠にはならない。

比率よりリスク

計算が中心なら unit を厚くし、DB の制約が中心なら integration の価値が高い。同じ業務シナリオを unit と HTTP の両方で確認することも、別の失敗を検出するなら意味がある。

エラー系には、不正入力、他人の ID、競合、二重送信、外部タイムアウト、キャンセルを含める。成功の呼び出し回数だけに過度に依存すると、内部の分割を変えるだけでテストが壊れる。

再現性と隔離

時刻、乱数、外部通信を制御し、テストごとにデータとモックの状態を戻す。実 DB は専用環境を使い、本番・共有開発データを消す初期化処理に接続しない。

カバレッジは実行された範囲であり、検証の質ではない。壊したときに検出できるか、失敗時に原因が分かるか、継続して実行できるかを確認する。

具体的な構成は NestJS のテストへ。
