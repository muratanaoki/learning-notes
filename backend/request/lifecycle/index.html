HTTPリクエストの処理順：NestJSで追う

ユーザー登録APIで処理順を追い、Middleware・Guard・Pipeなどがよく担当する処理と使い分けを学ぶ。

更新: 2026-09-28

HTTP APIには、届いた入力や実行権限を確かめ、本処理を行い、結果を応答にする役割がある。この章では、TypeScriptとNestJSで作るユーザー登録APIを例に、その役割がどこで実行されるかを見る。

学ぶ役割：受け取る → 入力や権限を確かめる → 登録する → 結果を返す。

これは処理の大枠。個々の検査を置く場所や順番はフレームワークと構成で変わる。以下ではNestJSの具体的な部品名と実行順を使う。

この章で追うのは、ユーザー登録の1リクエスト

ユーザーを登録するPOST /usersへ、次のJSONが届く。この例では、呼び出した利用者には登録を行う権限があるものとする。

{ "email": "ann@example.com", "age": 20 }

サーバーはメール形式と年齢を検査し、通ったら登録処理を呼ぶ。年齢が"twenty"なら、登録処理へ進まず400の応答を返す。同じ入力を、受信から応答まで追うのが今回の読み方だ。

NestJSの部品に当てはめて追う

各段の見出しが処理の役割、その横の英語名がNestJSで担当する部品。「入力検証で例外を投げる」を切り替えて、登録処理まで進む場合と、手前で止まる場合を比べよう。

説明パネルには、このリクエストで実行することと、その部品によく任せるほかの処理を載せている。「1手進む」や「手順を選ぶ」で止めながら読む。Cookie・キャッシュなどの用途例は、この登録APIで全部実行しているわけではない。

具体例：NestJSの POST /users

各段で「この例の動き」と「よくある担当」を読む。「1手進む」や「手順を選ぶ」で、気になる段を確認できる。

デモはNestJSで各部品を登録した場合の模型で、実際にAPIやDBへ登録するものではない。成功時はPOSTの標準の201 Created、入力エラー時は400を示す。登録範囲・複数の引数・エラーの扱いによって細かい順序が変わる。

コードで見る、ハンドラの位置

デモの「ユーザー登録」に当たるのが、次のメソッド。@Controller("users")を付けたUsersController内の抜粋で、importやServiceを受け取るconstructorは省略している。

@Post()
create(@Body() dto: CreateUserDto) {
  return this.usersService.create(dto);
}

@Post()がPOSTの処理、@Body()がJSON本文の受け取りを指定する。CreateUserDtoは受け取るデータの形で、次章で検査ルールを付ける。設定したPipeを通過するとこのメソッドが呼ばれ、UsersService.createへ登録を任せる。

入力エラーなら、このメソッドの本体には入らない。ここではControllerからServiceへ処理を分けているが、すべてのHTTP APIにこの分け方が必須なわけではない。

各部品でよく担当すること

「Middlewareはログだけ」「Pipeは年齢の検査だけ」と覚えず、何を知って判断する処理かで置き場所を考える。用途の見取り図は次のとおり。

部品よく担当する処理
MiddlewareリクエストID・アクセスログ・Cookieやセッションの準備
Guard本人確認・ルートの権限判定・呼び出し回数の制限
Interceptor処理時間の計測・応答の整形・参照結果のキャッシュ
Pipe入力の形式検査・型変換・余分な項目の拒否や除去
ControllerHTTPの入力を受け取り、対応する業務処理へ渡す
Service業務ルールの判断・保存や外部連携の段取り
Exception Filter未処理例外を公開用のステータスと本文へ変換

これらは、必要な機能を登録・設定した場合の用途。NestJSがすべてを標準で自動実行するという意味ではない。Interceptorの前半・後半は、同じ部品が処理を包む往路と復路だ。

Middleware：後続が使う共通の情報を準備する

この例のリクエストIDは、付けるだけでなく、ServiceのログやFilterのエラー応答にも渡して使う。アクセスログにはメソッド・パス・結果など、調査に必要な項目を選んで残す。Cookieを解析すること、セッションを読み出すこと、利用者の操作を許可することは、それぞれ別の仕事だ。

CORSやセキュリティヘッダーの設定も、HTTP入口の共通処理として扱う。Express用のMiddleware、Fastify用のプラグイン、NestJSやアダプタの標準機能などから構成に合うものを使う。すべてを自作のNestMiddlewareへ書く必要はない。Middlewareの適用対象はforRoutes(UsersController)のように指定できる。公式：Middleware、Cookie、Session。

GuardとPipe：権限の問いと、入力形式の問い

「ログインしているか」「管理者限定の操作を許可するか」はGuardで扱う。NestJSのThrottlerGuardのように、短時間に呼びすぎていないかを判定する使い方もある。公式：Guards、Rate limiting。

一方、「メール形式か」「URLのIDを整数へ変換できるか」「未指定のページ番号を1にするか」はPipeで扱う。ValidationPipe、ParseIntPipe、ParseUUIDPipe、DefaultValuePipeなどを目的に応じて設定する。GuardはPipeより先なので、URLや本文が検証済みだとは仮定しない。公式：Pipes。

ControllerとService：HTTPから業務へ渡す

Controllerは@Body()・@Param()・@Query()などで受け取った値を、対応するServiceへ渡す。Serviceは「登録できる条件を満たすか」「注文をキャンセルできる状態か」などを判断し、必要なDB更新や外部API呼び出しを進める。HTTP以外のジョブから同じ業務処理を呼ぶ場合も、この分担を使える。

DBアクセスを分離するなら、ServiceからRepositoryを呼び、その中でPrismaなどを使う。小さな構成ではServiceからPrismaを直接呼ぶ選択もある。Service・RepositoryはNestJSが順番に自動実行するHTTPの段ではなく、アプリが呼ぶ部品だ。

「同じメールを登録しない」は、Pipeのメール形式検査だけでは守れない。Service側で扱う業務条件と、同時登録も防ぐDBの一意制約・トランザクションを合わせて考える。対象データの所有者や状態も、読み書きの条件に含める。

Interceptor：本処理の前後に共通機能を加える

計測の開始・終了、JSONの形をそろえる処理、非公開項目を除くシリアライズ、待ち時間の上限設定などが代表例。ClassSerializerInterceptorでは、返すクラスや変換規則に沿って公開項目を制御する。導入しただけで任意の戻り値から秘密が自動で消えるわけではない。公式：Interceptors、Serialization。

参照用APIでは、キャッシュがあれば本処理を省き、なければ取得結果を保存する構成もある。利用者別の結果を混ぜないキーや有効期限を決める。このPOST /usersの登録例には適用しない。成功・エラー・終了の違いはInterceptorの記事で詳しく扱う。公式：Caching。

Exception Filter：失敗を利用者へ伝える形にする

入力不正を400、対象なしを404、状態競合を409へ対応付け、エラーコード・メッセージ・問い合わせ用のリクエストIDをそろえる、といった使い方がある。NestJSの標準処理で足りる場合もあり、独自のFilterは公開形式や記録方法を調整するときに使う。公式：Exception filters。

未知の障害は内部ログに原因を残し、利用者には安全な汎用メッセージを返す。入力不正まで一律に500へ変えたり、SQLやスタックをそのまま公開したりしない。詳細は例外フィルタと公開エラーの契約へ。

同じ「ログ」「検査」でも置き場所が変わる

  • リクエストが届いた記録はHTTP入口、ハンドラ周辺の処理時間はInterceptor、登録が確定した記録は業務処理に対応させる。Interceptorだけでは、その前のGuardで拒否された通信を観測できない。
  • 入力の形式はPipe、ルートへのアクセス権限はGuard、対象データの状態や更新条件はService・DBへ結び付ける。
  • 再試行で業務を回復する判断はServiceなど処理を知る側、回復できず残った例外の公開形式はFilterで扱う。

NestJSでの登録範囲と帰り道

Guard は通常 global → controller → route の順。Interceptor も入口は外側から内側へ進み、戻りの処理は内側から外側へ戻る。

Filter は通常 route → controller → global と近い範囲から候補が探される。1つが捕捉した例外を、残りの Filter が順に加工するチェーンではない。

エラーの場合

Pipe や Service が throw したときは、包んでいる Interceptor の catchError で変換したり、finalize で終了を観測したりできる。未処理なら Filter に届く。単純に「例外が出たらすべての Interceptor を飛ばす」わけではない。

一方、Guard で拒否された処理はその内側の Interceptor へ入らない。HTTP 外のジョブや fire-and-forget の失敗も、この HTTP Filter が自動ですべて拾うわけではない。

登録と DI

依存注入が必要な global Guard / Interceptor / Filter は、Module の APP_GUARD などの Provider 登録を使う方法がある。手動で new したインスタンスと、DI が組み立てるインスタンスを混同しない。

次は、Pipeで入力の中身を確かめる

デモで「入力検証で例外を投げる」を選ぶと、Pipeからハンドラへ進まず、エラー応答へ向かった。では、Pipeは何を見て入力を不正と判断するのだろう。

次の入力検証：届いたJSONをPipeとDTOで確かめるでは、ユーザー登録の年齢に"twenty"が届く例から始める。受け取りたいデータの形を表すDTOと、届いた値を調べるValidationPipeの役割を分けて読む。

この先は、入力検証→失敗時の応答→アクセス判定→前後の共通処理の順に学ぶ。アプリ全体の起動・終了は別のライフサイクルだ。
