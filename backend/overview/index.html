バックエンド設計の地図

TypeScriptとNestJSの具体例で、HTTP・認証・DB・テストから業務の設計と分散処理までを学ぶ。

更新: 2026-09-28

バックエンドの仕事は、リクエストに応じて許可された操作を、安全に実行し、結果を返すこと。設計パターンの名前より先に、1本の処理と、その途中の失敗を追う。

このセクションでは、アプリケーションの処理・データ・業務ルールを学ぶ。実行環境・デプロイ・監視と運用は、独立したインフラのセクションで学ぶ。まず知りたい側から読み始め、ログや障害対応など両方に関わる箇所は記事間のリンクでつなぐ。

TypeScriptとNestJSで、具体例から学ぶ

アプリケーションのコード例はTypeScript、HTTPサーバーはNestJSに揃える。 DBとORMにはPostgreSQL・Prismaを使う。まず「ユーザーを登録する」など一つの操作を決め、届くJSON、呼ばれるメソッド、保存する値、返す応答を追う。

「入力を確かめる」「実行を許可する」「失敗を応答にする」といった役割を、NestJSのPipe・Guard・Filterなどに対応させて読む。役割を他の技術へ応用するときも、部品の名前や厳密な実行順は、そのフレームワークの仕様を確認する。

ここで扱うコードは学習用の例。Sukimaの現在の構成はSukima Studyの地図を参照する。例に出る決済・Redis・キューなどが、すべて実サービスに導入されているわけではない。

図のログ・メトリクス・トレースをどう集め、調査に使うかは、インフラの可観測性で扱う。

初めて読む順序

  1. リクエストの一生 → REST：入口から応答までの契約。
  2. 認証と認可：本人確認と、操作対象ごとの権限判定。
  3. ORM と Prisma → トランザクション：永続化と同時更新。
  4. テストの分け方 → NestJSのテスト：成功だけでなく失敗を確かめる。
  5. SOLID → レイヤード → ドメインモデル → DDD：責任と業務の境界。
  6. メッセージキュー → 冪等性 → Outbox → Saga：非同期・分散処理の失敗と整合性。

TypeScript の型・Promise・モジュールが曖昧なら、型と実行時を先に読む。SQL の前提は リレーショナルモデル、プロセスと待機の前提は OS とシステムにある。

困りごとから深掘りする

困りごと読む記事
変更のたびに無関係な機能が壊れる凝集度と結合度、レイヤード
DBや外部APIを単体テストから切り離したいリポジトリ、依存性逆転
同じ言葉の意味が部署ごとに違うDDD、境界づけられたコンテキスト
複数の値を一緒に正しく保ちたい集約、トランザクション
一覧取得が遅いN+1、実行計画、キャッシュ
再送で処理が二重に走る冪等性
DB更新とメッセージ送信が片方だけ成功するOutbox
読み書きのモデルが複雑になったCQRS とイベントソーシング

導入を増やす前に

SOLID・DDD・CQRS・Kubernetes は、バックエンドを作るために全部必要なセットではない。まず要求と現在の問題を定め、少ない構成で満たせるかを見る。

  • インターフェースを増やしても、DBの制約・認可・同時更新対策は代替できない。
  • サービスを分割すると、関数呼び出しだった場所にネットワーク障害と運用が増える。
  • キャッシュや読み取り専用DBには、鮮度・無効化・復旧の責任が増える。
  • 機能を動かす実装と、障害時にも約束を守る実装を分けずに考える。
