SOLID 原則

変更に強いオブジェクト指向設計をつくる 5 つの設計指針を、悪い例と良い例で並べて掴む

更新: 2026-09-06

コードが動くことと、コードが直せることは別の話だ。動くだけなら 1 つの巨大なクラスに全部詰めてもいい。だが半年後に「決済を 1 種類足したい」となったとき、その 1 行の変更が無関係な機能まで巻き添えにするなら、その設計は失敗している。SOLID は、オブジェクト指向で「変更の波及をできるだけ小さく閉じ込める」ための 5 つの設計指針の頭文字だ——S・O・L・I・D。それぞれ角度は違うが、狙いは 1 つ、変更に強い構造をつくることに収束する。

各原則を、変更の影響範囲とコード例から比較する。

S — 単一責任

単一責任の原則 クラス（モジュール）が変更される理由は 1 つだけであるべき、という原則。「保存の都合」と「表示の都合」を同じクラスに同居させない。 は、1 つのクラスに責任を 1 つだけ持たせる。破ると、保存ロジックを直したついでに整形や通知が壊れる——「変更理由」が複数同居しているせいで、片方をいじると他方が巻き添えになる。守ると変更が 1 箇所に閉じ、テストも書きやすい。

// ⚠️ 保存・整形・通知が 1 クラスに同居
class User {
  save() {}
  toCSV() {}
  sendMail() {}
}

変更理由ごとに割るとこうなる。

// ✅ 変更理由ごとに分割
class User {} // データ
class UserRepository {} // 保存
class UserCsvExporter {} // 整形
class Mailer {} // 通知

O — 開放閉鎖

開放閉鎖の原則 拡張に対して開き、修正に対して閉じよ、という原則。機能追加のときに既存コードを書き換えず、新しいコードを足すだけで済む形を目指す。 は、機能追加のたびに if を増築するのをやめ、新しい実装を足すだけで拡張できる形にする。分岐の巣は、追加のたびに既存コードを開いて（＝壊すリスクを負って）いる状態だ。抽象を切っておけば、既存には手を触れない。

// ⚠️ 決済を足すたびに、この関数を「開いて」書き換える（既存を壊すリスク）
function charge(method: string, amount: number) {
  if (method === 'card') { /* ... */ }
  else if (method === 'paypay') { /* ... */ }
  // 新決済のたびに、ここに else if を増築していく
}

抽象を切ると、追加は「新クラスを 1 個足すだけ」になる。

// ✅ 決済手段は「足すだけ」、既存コードは不変
interface PaymentMethod {
  charge(amount: number): void;
}
class Card implements PaymentMethod {
  charge(a: number) {}
}
class PayPay implements PaymentMethod {
  charge(a: number) {}
}
// 新決済 = 新クラスを1個足すだけ。上の if の増築は丸ごと消える

L — リスコフの置換

リスコフの置換原則 派生型（サブクラス）は、基底型と入れ替えても正しく動かねばならない、という原則。継承は「振る舞いの契約」を守れるときだけ使う。 は、サブクラスを親のつもりで使っても契約が壊れないことを要求する。有名な罠が「正方形は長方形の一種だから継承」だ。

class Rectangle {
  protected w = 0;
  protected h = 0;
  setWidth(w: number) { this.w = w; }
  setHeight(h: number) { this.h = h; }
}
// ⚠️ 正方形は「幅=高さ」なので、幅を変えると高さも変わる
class Square extends Rectangle {
  setWidth(w: number) { this.w = this.h = w; }
  setHeight(h: number) { this.w = this.h = h; }
}

// 長方形として扱う側は「幅と高さは独立」を前提にしている
function resize(r: Rectangle) {
  r.setWidth(5);
  r.setHeight(4);
  // Rectangle なら面積 20 のはず。だが Square を渡すと 16 になる ← 置換で壊れた
}

Square は Rectangle の「幅と高さは独立に変えられる」という契約を破っている。だから継承は「is-a（正方形は長方形だ）」で決めてはいけない——「親のフリで差し替えても振る舞いが保たれるか」で判断する。保たれないなら、継承ではなく別物として分ける。

I — インターフェース分離

インターフェース分離の原則 使わないメソッドへの依存をクライアントに強制しない、という原則。太った 1 枚のインターフェースを、役割ごとの小さな口に割る。 は、巨大な 1 枚のインターフェースを役割ごとに割る。work / eat / sleep を 1 枚にまとめると、eat の要らない Robot が空実装や例外送出を強いられる。必要な口だけを実装できるよう、小さく分ける。

// ⚠️ 太い 1 枚 → 使わない口の空実装を強制
interface Worker {
  work(): void;
  eat(): void;
}

役割ごとに割れば、必要な口だけ選んで実装できる。

// ✅ 役割ごとに分離
interface Workable {
  work(): void;
}
interface Eatable {
  eat(): void;
}
class Robot implements Workable { work(): void {} } // eat に縛られない

D — 依存性逆転

依存性逆転の原則 上位モジュールも下位モジュールも抽象に依存すべきで、抽象を具体に依存させてはならない、という原則。業務ロジックを技術の詳細から切り離す。 は、業務ロジックが具体的な DB や API を直接 new するのをやめ、抽象（インターフェース）にだけ依存させる。上位（業務）が技術の詳細に縛られなくなり、実装を自由に差し替えられる。

// ⚠️ 業務が具体（Prisma）を直接 new → DB を替えると業務まで書き換え
class GetUser {
  private repo = new PrismaUserRepository();
}

あいだに抽象を挟むと、業務は具体クラスの名前を知らなくなる。

// ✅ 業務は「口（抽象）」にだけ依存 → 具体は外から渡す
interface UserRepository {
  findById(id: string): Promise<User | null>;
}
class GetUser {
  constructor(private repo: UserRepository) {} // 具体クラスを知らない
}

依存の向きが「業務 → 具体」から「業務 → 抽象 ← 具体」へ裏返るのがこの原則だ。5 つの中でも設計に効く度合いが大きく、リポジトリパターンや DI（NestJS の DI コンテナ）と直結する。実際の配線（抽象トークン・@Inject・Module）は 依存性の逆転 で単独で深掘りするので、ここでは「具体依存 → 抽象依存への裏返し」という骨だけ掴めばいい。

分割のコストも測る

SRPは「1クラス1メソッド」ではない。OCPも既存コードの修正禁止ではなく、変化しやすい部分を契約の外へ出す指針。新実装を選ぶ配線や設定、契約テストは追加時に変更する。具体クラスを直接使うこと自体が違反なのではなく、守りたい業務が外側の詳細に結び付いているかを確認する。

LSPでは型が一致するだけでなく、事前条件・事後条件・例外・副作用の約束を守る。空実装でコンパイルだけ通すのも契約違反になりうる。

5 つを一望する

記号原則破ると困ること守ると得られること
S単一責任1 つの修正が無関係な機能を壊す変更が 1 箇所に閉じる
O開放閉鎖追加のたびに既存を開いて壊す足すだけで拡張できる
Lリスコフの置換継承先が親の前提を裏切る安心して差し替えられる
Iインターフェース分離要らない口の空実装を強いられる必要な機能にだけ依存
D依存性逆転業務が技術の詳細に縛られるテスト・差し替えが効く

どれも独立した掟に見えて、根は同じだ。責任を割り（S）、実装を足せる口をつくり（O・I）、その口の契約を守り（L）、上位を口にだけ依存させる（D）——全部が「変更の影響範囲を小さく囲う」ための別の言い回しになっている。教条として全部を一度に満たそうとするより、痛みが出た箇所に対応する原則を当てるのが実務的だ。

次へ

SOLID の 5 原則は、突き詰めると 2 つの物差しを良くするための手立てだ——S は一つのモジュールのまとまり（凝集度）を上げ、D はモジュール同士の絡み（結合度）を下げる。この 2 つの物差しそのものを、次の凝集度と結合度で正面から見る。良い設計を測る最小の言葉になる。
