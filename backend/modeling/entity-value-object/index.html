エンティティと値オブジェクト

ドメインの部品はIDで区別する「もの」と、値そのものが等しければ等価な「値」の2種類に分かれる

更新: 2026-09-06

ドメインモデルを組み立てる部品は、まず同一性の扱いで、エンティティと値オブジェクトを区別する。1 つは「同じもの」であり続けることが本質の部品——User は名前を変えても、Order は状態が進んでも、銀行口座 は残高が動いても、同じ 1 つの存在だ。もう 1 つは、値そのものが意味のすべての部品——1000 円 は、いつどこの 1000 円でも同じ 1000 円でしかない。前者を エンティティ ID(同一性)で区別される部品。属性が変わっても、ID が同じなら「同じもの」であり続ける。User・Order・銀行口座など、ライフサイクルを持つ存在。 、後者を 値オブジェクト ID を持たず、値そのものが等しければ等価とみなす部品。不変で、変更は新しいインスタンスの生成として表す。Money・Address・DateRange・座標など。 と呼ぶ。両者は何をもって「等しい」とするかが根本的に違う。

先に誤解を 1 つ解いておく。この 2 分類は DDD の本で有名になったが、DDD 専用の道具ではない。値オブジェクトは Evans 以前からある汎用パターンで、クリーンアーキテクチャの中心の円に置いても、何のアーキテクチャも採らない素の TypeScript でもそのまま使える。「UserId 型を作って string の取り違えを防ぐ」——それだけでもう値オブジェクトだ。方法論への入信は要らない。

下のトグルで、同じデータを「値オブジェクトとして」比べる場合と「エンティティとして」比べる場合を切り替えてみて。属性や ID を変えたとき、等しさの判定がどう反転するかに注目。

値オブジェクトとして比較エンティティとして比較

ID は見ない（そもそも持たない）。金額が同じなら「同じ 1000 円」。属性を 1 つ変えれば、それは別の値——1000 円を 1500 円に「変更」したのではなく、新しい 1500 円を作った、と考える（不変）。

同一性 vs 等価性

違いは一言でいえば、何を見て「同じ」と判断するかに尽きる。

  • 同一性(identity) そのものが「同じ個体か」を問う概念。ID で判定する。属性が全部違っても ID が一致すれば同じ、属性が全部同じでも ID が違えば別。エンティティの等値判定。 ：エンティティが使う。ID だけを見る。残高が 1000→2000 に変わっても、口座番号 #001 は同じ口座。
  • 等価性(equality) 値として「同じ内容か」を問う概念。全属性を見て判定する。ID の概念はない。値オブジェクトの等値判定で、同じ値なら常に交換可能。 ：値オブジェクトが使う。属性の中身を見る。1000円 と 1000円 は、別インスタンスでも等価で、交換可能。

コードにすると、equals の中身がそのまま分岐点になる。

// エンティティ：ID だけで同一性を判定する
class Account {
  constructor(readonly id: string, private balance: number) {}
  deposit(amount: number) { this.balance += amount; } // 同じ口座のまま状態が変わる
  equals(other: Account) { return this.id === other.id; } // 属性は見ない
}

// 値オブジェクト：全属性で等価性を判定する（ID は無い）
class Money {
  constructor(readonly amount: number, readonly currency: string) {}
  equals(other: Money) {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

値オブジェクトは不変

値オブジェクトのもう 1 つの柱が 不変(immutable) 生成後に状態を変えられない性質。値オブジェクトは変更メソッドを持たず、変更に相当する操作は新しいインスタンスを返す。共有しても壊れず、等価性の前提を保てる。 だ。1000円 の中身を書き換えるのはおかしい——それは別の値になる。だから値オブジェクトに「変更」は無く、変更に見える操作は新しいインスタンスを返す。

class Money {
  constructor(readonly amount: number, readonly currency: string) {
    if (!Number.isSafeInteger(amount) || amount < 0) throw new Error('金額は非負の安全な整数で指定'); // 不正な値を存在させない
  }
  add(other: Money): Money {
    if (this.currency !== other.currency) {
      throw new Error('通貨が違う'); // JPY + USD を静かに足させない
    }
    return new Money(this.amount + other.amount, this.currency); // 自分は変えず新品を返す
  }
}

const a = new Money(1000, 'JPY');
const b = a.add(new Money(500, 'JPY')); // a は 1000 円のまま、b が 1500 円

ここが実務で効く。金額計算・通貨チェック・負数の禁止といったロジックを値オブジェクトに寄せると、不正な状態のインスタンスがそもそも作れない。number で持ち回るより、Money 型が自分で自分を守る。

もう 1 つ、生の number／string のまま持ち回らない利点がある——意味を型にすると、取り違えがコンパイルで弾ける。

// ⚠️ プリミティブのまま：金額と数量を逆に渡してもコンパイルが通ってしまう
function order(amount: number, quantity: number) {}
order(qty, price); // 逆でも動いてしまい、気づけない

// ✅ 値オブジェクト：型が意味を持つので、取り違えはコンパイルエラー
function order(amount: Money, quantity: Quantity) {}
order(quantity, money); // ← ここでコンパイルが落ちる

「何でも number・何でも string」で引き回す癖はプリミティブ執着（primitive obsession）と呼ばれる典型的な設計の匂いで、値オブジェクトはその解毒剤でもある。

見分け方

迷ったら「ID を振って追跡したいか、値が同じなら入れ替えても構わないか」を問う。

観点エンティティ値オブジェクト
区別のしかたID(同一性)値(等価性)
属性が変わると同じもののまま別の値になる
可変性ライフサイクルを追う。不変な表現も可能不変な値として扱い、新しい値へ置き換える
ID持つ持たない
例User, Order, 銀行口座Money, Address, DateRange, 座標
判断の問い追跡・履歴が要るか値が同じなら交換可能か

同じ概念でも文脈で変わる点に注意。住所は多くの場合 Address という値オブジェクトだが、「配送先マスタ」として 1 件ずつ ID で管理・改訂履歴を追うなら、その文脈ではエンティティになる。部品の種別はモデルの都合で決まる——絶対的な正解表があるわけではない。

型と実行時の限界

上のMoneyは最小通貨単位を整数で持つ簡略例。負の金額を許すかは業務次第で、丸め・通貨の桁数・上限を別途定める。JavaScriptの readonly は静的な代入制限で、深い実行時不変性ではない。型の取り違え防止も構造的型付けでは同じ形の型に注意し、必要ならbrandやprivateな生成経路を使う。

ドメインとフレームワークの境界

エンティティと値オブジェクトは、それ単体では NestJS の話が一度も出てこないことに気づいたはず。それは意図的で——ドメインモデルはフレームワークに依存しない、素の TypeScript クラスであるべきだ。@Injectable() や @Entity() のようなデコレータを Money や User に付けない。付けた瞬間、そのクラスは NestJS(や ORM)を知ってしまい、フレームワークを差し替えるたびにドメインまで書き直す羽目になる。

// 値オブジェクト：プレーンな TS クラス。デコレータは一切付けない
class Money {
  constructor(readonly amount: number, readonly currency: string) {
    if (!Number.isSafeInteger(amount) || amount < 0) throw new Error('金額は非負の安全な整数で指定');
  }
  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error('通貨が違う');
    return new Money(this.amount + other.amount, this.currency);
  }
}

// エンティティ：これもプレーンな TS クラス。ID で同一性を判定する
class User {
  constructor(
    readonly id: string,
    private name: string,
    private balance: Money,
  ) {}
  equals(other: User): boolean {
    return this.id === other.id; // 属性は見ない、ID だけ
  }
  charge(amount: Money): void {
    this.balance = this.balance.add(amount); // 状態が動く＝エンティティらしい振る舞い
  }
}

デコレータが付くのは、この外側にいる Service の方だ。NestJS のコンテナに登録される必要があるのは「ユースケースを実行する層」であって、ドメインそのものではない。

import { Injectable } from '@nestjs/common';

// @Injectable() は Service に付く。Money/User はただの値として組み立てて使うだけ
@Injectable()
class RegisterUserService {
  register(id: string, name: string): User {
    const initialBalance = new Money(0, 'JPY'); // ドメインのクラスを普通に new するだけ
    return new User(id, name, initialBalance);
  }
}
