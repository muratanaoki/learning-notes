ハッシュテーブル

ハッシュで候補の場所を決め、キー比較で確かめる。衝突・負荷率・リハッシュの条件。

更新: 2026-09-06

ハッシュテーブルは、キーを計算して置き場所（番号）を直接出すデータ構造。「どこにあるか」を比較で探すのではなく、置き場所そのものを計算で決めて直行するので、検索・挿入・削除が平均 O(1)。辞書・Map・Setの代表的な実装だが、名前だけで内部構造がハッシュに限定されるわけではない。

キー → 番号 → 直行

キーを追加・検索すると、まず ハッシュ関数 キーを固定長の数値に変換する関数。同じキーは必ず同じ値になる。 で番号（バケット）を計算し、そこへ直行する。同じ番号に複数入ると 衝突 異なるキーが同じバケット番号になること。避けられないので、うまくさばく仕組みが要る。 。

キーを計算でバケット番号に変換して直行する。だから平均 O(1)。同じ番号に重なった分だけ（衝突）チェインを辿る。

仕組みは3ステップ

  1. ハッシュ関数でキーを数値にする（例：文字コードの合計）
  2. バケット数 M で割ったあまりを番号にする（0〜M−1 に収める）
  3. その番号のバケットに置く／から取る

添字アクセスと同じで、番号さえ出れば一発。「どこにあるか」を探すのではなく「どこに置くか計算で決める」のが核心。

function hash(key: string, M: number): number {
  let sum = 0;
  for (const ch of key) sum += ch.charCodeAt(0);
  return sum % M; // 0..M-1 のバケット番号
}

衝突は避けられない

キーは無数、バケットは有限。必ず別のキーが同じ番号に来る（ 誕生日のパラドックス 23人いれば誕生日が一致するペアが50%を超える、という直感に反する確率の話。ハッシュ衝突が思ったより早く起きる根拠。 と同じで、思うより早く起きる）。主なさばき方は2つ。

  • チェイン法 … 同じバケットを連結リストにしてつなぐ（上の図がこれ）
  • オープンアドレス法 … 埋まっていたら次の空きバケットへずらして入れる

どちらも衝突が増えるほど遅くなる。埋まり具合（ 負荷率 要素数 ÷ バケット数。1に近づくほど衝突が増える。拡張の閾値は実装方式で異なり、チェイン法では1を超える場合もある。 ）が上がったらバケットを増やして全部入れ直す（リハッシュ）ことで O(1) を保つ。

操作ハッシュ平衡木（BST）
検索・挿入・削除平均 O(1)O(log n)
最悪O(n)（衝突集中）O(log n) 保証
キーの大小順・範囲検索得意ではない得意

「とにかく速く出し入れ」ならハッシュ、「大小の順序も欲しい」なら平衡木。用途で選ぶ。

同じハッシュ値は、同じキーではない

候補の場所へ届いたら、実際のキーの等しさを確認する。異なるキーが衝突しても別々に保持できることが必要。上の文字コード合計は説明用で、abとbaが衝突するため実用のハッシュ関数として推奨するものではない。

キーの文字数がkならハッシュ計算自体にO(k)かかる場合がある。リハッシュする1回はO(n)で、毎回の操作が必ず一定時間という保証でもない。

JavaScriptのMapのように挿入順を保つものもある。「大小順に効率よく探せない」と「いかなる順序も持てない」を区別する。
