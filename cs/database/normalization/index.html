正規化：事実と関数従属を分ける

候補キー・部分従属・推移的従属を理解し、更新異常を減らす。

更新: 2026-09-06

正規化は「同じ文字列を全部1箇所にする」操作ではない。事実の粒度と関数従属を整理し、更新・挿入・削除で矛盾が起きにくい表へ分解する。

非正規形1枚の表に全部詰め込んだ状態。1つのセルに複数の商品が入っている。
注文明細（非正規形）
🔑注文ID顧客名住所商品単価
1001田中東京りんご, みかん100, 80
1002佐藤大阪りんご, バナナ100, 120
この段で残っている問題
  • ✗1つのセルに複数の値（繰り返し列）
  • ✗顧客名・住所が行の数だけ重複（部分関数従属）
  • ✗同じ商品の単価があちこちに重複（部分関数従属）
  • ✗住所が「注文→顧客」経由で重複（推移的関数従属）

段を進めるほど表は増えるが、同じ事実は1か所だけに置かれる。だから値を直すのも一度で済み、更新異常が消える。

デモの商品価格は「商品ごとに決まる現在の価格」という前提の例。注文時価格の履歴とは分けて読む。

異常の原因

1つの表に注文と商品の情報を混ぜると、商品名変更を全注文行へ反映する必要が生じる。注文がない商品を登録できず、最後の注文を削除したら商品情報まで消えることもある。

これらは1つの行に異なる種類の事実を持たせたことが原因だ。

関数従属と候補キー

X の値が決まると Y が一意に決まることを X → Y と書く。たまたま現在のデータで一致するだけでなく、業務上常に成立する条件で判断する。

候補キーは行を一意に決める最小の属性集合。そのうち1つを主キーとして選ぶ。正規化では選んだ主キーだけでなく、すべての候補キーを考える。

各正規形

形確認すること
1NF採用した値のドメインに沿い、繰り返しの組を行へ整理する
2NF1NF で、非キー属性が候補キーの一部だけに依存しない
3NF非自明な従属 X → A について、X がスーパーキーか、A が候補キーの構成属性
BCNF非自明な従属の決定側がスーパーキー

入門的には「2NF で部分従属、3NF で非キー属性を経由する推移的従属を除く」と読める。候補キーが複数ある場合などは正式な条件を使う。

分解の例

OrderLine(orderId, productId, quantity, productName) で、1注文1商品1行なら候補キーは (orderId, productId)。productId → productName は一部への依存なので商品名を Product へ分ける。

人工的な id を追加しても、商品 ID から商品名への従属は消えない。「単一列の主キーにしたから正規化完了」にはならない。

分解後に JOIN で元の事実を正しく復元できるか、必要な従属を守れるかを確認する。過去の単価や住所は別の事実なので現在のマスタへ一律に統合しない。
